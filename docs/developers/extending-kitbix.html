Extending Kitbix

Add features to the free Kitbix Commerce plugin without touching core files. Use hooks, addons, REST endpoints, and MU-plugins to keep upgrades painless.

Extension checklist

  1. Choose the integration surface: hook (UI tweaks), addon (modular feature), REST/React (headless), or shortcode override.
  2. Prototype in a separate plugin: autoload classes via Composer or a simple PSR-4 map. Register hooks on plugins_loaded.
  3. Target staging first: use wp-env or a cloned site, seed data, and run regression smoke tests.
  4. Document the change: note file paths, hook names, and rollback steps; commit to VCS alongside your theme/plugin.
  5. Ship + monitor: enable feature flags or toggle addons per site when rolling updates to production.

Addons vs. hooks

When to build an addon

  • You need settings surfaced in Kitbix → Addons.
  • You must enqueue assets, register product fields, or inject markup automatically.
  • Logic should toggle on/off per site without touching code.

Implement AddonContract, register via kitbix_commerce_register_addons, and guard runtime logic behind AddonRegistry::isEnabled().

When hooks are enough

  • Quick UI injections (kitbix_commerce_after_product, kitbix_commerce_checkout_after_payment_methods).
  • Lifecycle handlers (kitbix_commerce_order_created, kitbix_commerce_product_saved).
  • Cart/checkout filters (kitbix_commerce_cart_totals). No settings UI required.

Working with REST + JS

  • Use the native admin SPA components where possible. Admin routes already exist for products, orders, addons, settings, and analytics.
  • Register new routes by extending KitbixCommerce\Controllers\Controller and adding entries to routes/admin.php or routes/public.php.
  • Frontend React features (admin/react-app) consume Redux slices; wrap new API calls with createAsyncThunk patterns similar to analyticsSlice.js.

Deployment patterns

  • MU-plugins for shared logic: load enterprise-specific hooks/addons before Kitbix initializes.
  • Composer-managed packages: publish internal addons as libraries, then require them in wp-content via path repositories.
  • Feature flags: use options/transients to toggle risky behavior gradually. Always bail when flags are off.
  • Testing: pair PHPUnit for service classes with Cypress/Playwright for storefront smoke tests.

Tips & best practices

Tip: Namespaces matter—follow KitbixCommerce\ conventions or your own PSR-4 root to avoid class collisions.
Tip: Cache expensive API calls or queries and invalidate them via lifecycle hooks (order/product events).
Tip: Make custom code resilient. If Kitbix deactivates, your plugin should bail gracefully and not fatal.

Common mistakes

  • Forking Kitbix core and missing security releases.
  • Embedding business logic inside shortcodes instead of moving it to addons/services.
  • Running direct SQL without $wpdb->prepare() or the Database::table() helper.
Reminder: Keep extensions reversible. Track every customization in source control and note how to disable it quickly during incidents.
